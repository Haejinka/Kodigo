# Typed API and command contracts

Supplement to ARCHITECTURE A02/A03; normative for the lower-tier implementation model. These are proposed APIs, not existing deployed endpoints. All writes use Supabase RPC with `{p_command: CommandV1}` and thin frontend adapters. Read methods use typed parameters listed below, not arbitrary SQL/filter strings. Never expose private posting helpers. Task owners create the exact TypeScript payload/result types in their declared domain files.

## Command envelope, validation and errors

`CommandV1` fields: `contract_version:1`, `operation_id:UUID`, `store_id:UUID`, `terminal_id:UUID|null`, `shift_id:UUID|null`, `occurred_at_local:ISO8601|null`, `terminal_sequence:integer|null`, `expected_version:integer|null`, `payload:object`. Actor is session-derived; no arbitrary actor override. Required terminal/shift is checked by command kind. A supervisor recovery command supplies a lease/source reference, never an unchecked original-cashier parameter.

Quantities are positive integers for current sale/intake APIs. Money and rates returned as canonical decimal strings/integer basis points; reject NaN/infinity/negative values outside allowed signed movement commands. IDs, states, reasons and method enums are validated before casts/writes. New operational requests cap reason3–500 chars and free comments1–2000; external references1–160 with B08 normalization. Unsupported extra fields reject, so old/new payload interpretation cannot drift silently. Current supported tender remains cash/gcash/card/bank_transfer/other. Apply tasks explicitly register command kinds and supported contract version; no dynamic SQL/table/function dispatch.

`CommandResultV1`: contract_version, operation_id, outcome (`confirmed` or `pending_external`), aggregate_type/id/version, confirmed_at server timestamp, result domain object. `confirmed` means the **command** committed (a request can commit while its workflow remains requested); result always includes workflow_state. It does not mean provider settlement/printing finished. Client local result is separate `{outcome:'recorded_locally',local_id,queue_state,occurred_at_local}` where `queue_state` follows B09 (`local_pending`, `syncing`, `synchronized`, `retry_wait`, `conflicted`, `blocked_auth`, or `needs_recovery`). A client-computed integrity hash excludes `operation_id`; the server recomputes its hash from validated semantic fields and checks operation ID, actor, store, terminal and command kind independently.

Expected validation failures raise stable business error detail JSON `{business_code,message,field_errors?,current_version?,retryable:false}` using a consistent SQL error category, preserving SQLSTATE42501 for authorization where appropriate. Codes: AUTH_REQUIRED, MFA_REQUIRED, STORE_FORBIDDEN, CAPABILITY_REQUIRED, SELF_APPROVAL, SELF_GRANT, FEATURE_DISABLED, INVALID_INPUT, UNSUPPORTED_CONTRACT, UPGRADE_REQUIRED, IDEMPOTENCY_MISMATCH, VERSION_CONFLICT, INSUFFICIENT_STOCK, INSUFFICIENT_CASH, INSUFFICIENT_WALLET, RETURN_LIMIT, CREDIT_LIMIT, REFUND_LIMIT, SALE_INELIGIBLE, SETTLEMENT_REQUIRED, DUPLICATE_EXTERNAL_REFERENCE, SHIFT_REQUIRED, SHIFT_CLOSED, LEASE_EXPIRED, LEASE_REVOKED, GRANT_EXHAUSTED, SEQUENCE_GAP, LEGACY_RECONCILIATION_REQUIRED. Domain failure rolls back all command effects and does not create committed success. Client preserves same ID for transport retry; a deliberately changed proposal uses a new ID linked to previous request.

Transport errors/5xx/429 are handled separately from domain errors. A failed offline ingest is captured in local durable conflict state and can be recorded through a separate checked `record_sync_conflict` command after the failed transaction. Do not catch an exception halfway through accounting and report partial success. `get_pos_operation(p_store_id,p_operation_id)` returns prior committed response only to original authorized actor or explicitly authorized recovery reviewer.

Inventory product creation must submit initial stock through the central opening-stock service in the same transaction as new product/option metadata, not a generic independently queued INSERT. New offline generic catalog/PO writes are unsupported.

## Customer, queue and paginated reads

Customer profile/search/association commands (T43): `create_customer`, `update_customer`, `archive_customer`, and `associate_sale_customer` accept the standard `CommandV1` envelope through `p_command`. Create payload is `{display_name,phone,email}` with nullable contacts and `expected_version:null`; update is `{customer_id,display_name,phone,email}` with the current customer version; archive is `{customer_id,reason}` with the current version; retroactive association is `{sale_id,customer_id,reason}` with the current customer version. The server derives actor/store authority, requires `manage_customers` for profile writes and association, and returns IDs/version only in the committed operation result. Each mutation and its `pos_operations` result commit together. `search_customers(p_store_id,p_query,p_limit)` is available to assigned admins/cashiers and returns only active `{id,display_name}` rows (name prefix or exact phone search); `get_customer(p_store_id,p_customer_id)` returns profile/contact fields only to an actor with `manage_customers`. Direct table access is denied. Checkout customer selection is optional; no profile is forced or auto-created and no sale is automatically matched by identity/contact fields. Unselected sales keep `customer_id` null. No names/phones are merged; association updates only nullable `sales.customer_id` and appends one immutable event, without rewriting receipt snapshots. Contact retention/redaction remains gated by D07. `get_customer_history`, `get_customer_summary`, and `get_customer_rankings` use the T45–T46 fact basis; they include explicitly linked sales only, while guest totals are separate; metrics are whitelisted and the current store is required. GCash principal is excluded from spending.

Timeline/list reads use `p_store_id`, typed `p_filters`, `p_cursor:null|opaque cursor`, `p_limit` default50/max100. Cursor includes sort tuple and filter hash; wrong store/filter rejects rather than silently paging another scope. Standard result `{items,next_cursor,has_more,generated_at,filters}`. Use `(created_at,id)` descending for histories and `(metric_value,customer_id)` for rankings with explicit direction/ties. Related detailed records have same-store authorization. No arbitrary client column/order expressions.

Offline lease RPCs follow A07. `issue_offline_lease(p_command)` accepts CommandV1 with the cashier's store, terminal and own active shift, null sequence/version, and empty payload; the server derives actor, MFA, issue/expiry, and sequence range. It returns a committed lease snapshot in `pending_stock`, which cannot authorize checkout. Each range is at most 100 operations for at most 8 hours, beginning at `last_confirmed_sequence + 1`; pending-stock ranges may be reused only after revocation/expiry before activation, while activated leases block reissue until reconciliation. `revoke_offline_lease(p_command)` accepts the lease's current `expected_version` and `{lease_id,reason}`; owner cashier or assigned store admin may revoke, and this never releases grants. `get_offline_lease(p_store_id,p_lease_id)` is scoped to an assigned admin or the owning cashier. None allow `super_admin` to bypass store membership. `allocate_offline_stock`, `release_reconciled_offline_stock`, `ingest_offline_pos_operation` and `record_sync_conflict` follow A07. T52 allocation attaches server-selected lots and quote snapshots and atomically activates the lease. Ingest payload contains immutable physical sale command plus lease_id, catalog/quote hash and per-line grant IDs/base quantities; caller identity must match lease unless invoking separately authorized supervisor recovery. One ingest RPC is one atomic sale. `syncPosOperations` is a client loop of at most20 separate requests, never a SQL multi-commit batch. Returned ack contains sale/receipt, operation/hash, sequence, original/server times, stock-grant/cash references and closeout adjustment if late. Store ack before advancing local lane.

Printing: existing `/v1/receipts/print` unchanged. New paired agent `GET /v1/capabilities` advertises document/profile support and the maximum native item count (50). `POST /v1/documents/shopping-list/print` accepts `{printerName,document_id,attempt_id,document_hash,profile:'58mm'|'80mm',reprint:false|true,show_prices,shopping_list:SnapshotV1}`. `SnapshotV1` is `{version:1,documentId,createdAt,storeId,storeName,items:[{productId,productName,quantity,purchaseUnit,unitPrice,subtotal,isEstimated}],total}`. `document_hash` is lowercase SHA-256 over `profile`, `show_prices`, and the compact JSON serialization of `shopping_list`; the agent recomputes it from the received snapshot. Unknown outcome is explicit reprint only, never money/sale retry logic. No database command or drawer pulse is issued.

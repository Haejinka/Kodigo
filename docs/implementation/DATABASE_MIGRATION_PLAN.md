# Database migration and integrity plan

This file specifies desired schema and migration ordering, **not executable migrations**. No SQL was applied. Do not edit historical migrations or run `supabase_schema.sql` over an existing database. PostgreSQL/Supabase versions and the actual migration chain must be established by T00.

## M00 — Reproducible baseline and safety gate

T00 creates `docs/implementation/SCHEMA_BASELINE.md` and `supabase/bootstrap-manifest.json` during implementation. The manifest records exact relative files/checksums/dependencies and the baseline records effective fingerprints of overlapping RPCs. Capture from an authorized isolated clone: server_version; applied migration history; `pg_get_functiondef` for process_pos_sale/v2/v3/v4, stock deduction, receive/adjust/void/return/refund/closeout helpers; `pg_trigger` including alphabetical trigger order; view definitions; RLS/policies/grants; all table types/constraints/indexes. Production read-only inspection is optional and must use the explicitly selected project; never infer project from arbitrary environment credentials. Implementation has since captured a read-only deployed snapshot; see SCHEMA_BASELINE.md. This is not an isolated clone and does not satisfy restore/equivalence verification.

Reconstruct a clean disposable project from a topologically sorted manifest and compare its effective schema/function fingerprints to a restored clone. This is necessary because root numeric and dated migrations overlap and some November migrations dynamically replace older function text. Keep legacy files intact; put any bootstrap correction in a forward migration. Restore-backed and empty-database paths must both pass. Missing root migration 33 is recorded as absent, not invented.

Discover installed CLI with `supabase --version` and `supabase --help`; if absent, choose and pin an explicitly reviewed version in the implementation task. Current official CLI documentation describes a v3 target-default change; never assume old `--linked` or db reset/push semantics. Use `--help` for the pinned version. Test DB connection comes only from `KODIGO_TEST_DATABASE_URL` and a guard against production identity. Integration Supabase URL/key variables remain separate. Do not run cleanup/reset on production.

## Shared conventions

- New primary IDs UUID; operation-owned IDs may be supplied by client, otherwise server generated. Timestamps `timestamptz`; creation/confirmation server-generated; local timestamps untrusted separate fields. Every mutable workflow has integer `version` incremented under row lock.
- Settled money `numeric(14,2)`, quantity `numeric(14,3)` for ledger/lot compatibility with explicit integer checks for current sale/base units, new movement-lot and source receipt/allocation cost `numeric(14,6)`, basis-point rate integer 0–10000. Deployed legacy `sale_items.cost_per_base_unit` is `numeric(12,4)` and `cost_price` is unconstrained `numeric`; retain those snapshots and do not imply they have six-decimal precision. Currency `text CHECK(currency='PHP')`. Do not narrow or rewrite existing historical columns.
- Every new operational table has store_id, created_at and actor where meaningful. All same-store relations use `(store_id,id)` unique target and composite foreign keys. Keep original global UUID PK. Audit FKs use RESTRICT; employee references nullable SET NULL only where immutable actor-name/ID snapshots preserve attribution. Archive stores/products/users; do not cascade-delete accounting history. Existing dangerous CASCADE relations require reviewed forward constraint replacements and compatibility test, not wholesale schema drop.
- RLS enabled on every public table; authenticated SELECT by existing MFA-aware membership plus role/capability. No ordinary direct INSERT/UPDATE/DELETE grants on ledgers. Public command RPCs are narrowly granted authenticated execute with auth/store/capability checks. Private helpers revoked from PUBLIC/anon/authenticated. Internal ownership may bypass RLS only through reviewed command gateway.
- Every FK used for lookup has an index (including source IDs not covered by a leading composite). Every timeline has `(store_id, created_at DESC, id DESC)` and product/customer-specific cursor index. Unique operation-derived source keys prevent retry effects. Add nullable columns/backfill/validate before NOT NULL. For large live tables, build indexes concurrently in a dedicated nontransactional deployment step after staging capacity review.
- New append-only triggers reject UPDATE/DELETE on posted facts, even through administrative application RPCs. Protected projection/workflow fields may change only through controlled functions. Corrections insert linked compensations. Deferred consistency checks inspect operation-owned rows, never full-table scans at each commit.

## Schema contracts (task-owned additions)

Migration paths below are **logical slugs**. Each SQL task creates its actual filename using the pinned CLI's `migration new <slug>` and records the returned path in `SCHEMA_BASELINE.md` and TASK_STATUS. The timestamp is the only intentionally deferred filename component; do not hand-invent one. Precise non-migration code/test paths are in each TASKS file.

Seed locations/balances from current product stock and proven lots. Do not invent historical lot costs/ownership or rebuild missing per-sale provenance. Mismatch blocks that product's cutover until authorized correction. The writer migration must replace all mutation triggers in one transaction and route old RPCs to the centralized helper. Movement append-only protection and direct stock-write denial must be active before enabling ledger_v2.

For lots, location_id means original receiving location; quantity_remaining is default-sellable projection, quarantine lives in lot-location balances. Do not infer location from one lot status when both locations contain quantity. Movement-lot rows additionally snapshot the original source unit_cost at six-decimal precision and cogs_recovery_amount numeric(14,2); only eligible restock/void/inspection release posts recovery. Canonical COGS uses these immutable recovery facts once, not a second subtraction from credit-line cogs_recovered. New net quantity_sold projection is allocated minus physical-returned minus void-restored; legacy values stay provenance-classified, and older sale-line cost precision is preserved as recorded in SCHEMA_BASELINE. No new lot receipt/payable is created for a retail return.

### M06 — Refund authorization and settlement (T20–T23)

`sale_refunds`: id/store/sale/operation/requester/approver/amount/method/state/version/reason/provider_account/ref normalized/reference evidence/current shift/reservation ID/timestamps; requester<>approver where an approval is required. `sale_refund_allocations`: refund/store/credit_item/original_payment/amount>0; unique(refund,credit_item,payment). `refund_settlement_events`: immutable refund/operation/outcome/reference/evidence/actor/time; one confirmed event per settlement leg. Original capture unused capacity and unused credit capacity include pending reservations. Unique normalized provider reference in external evidence table prevents duplicate internal posting. ### M07 — Drawers and cash ledger (T24–T27)

- `pos_terminals`: id/store/name/display_identifier/registered_by/active/device_public_metadata; stable registered UUID, never browser-provided display string as identity.
- `cash_drawers`: id/store/name/terminal association/active; logical custody independent of hardware drawer pulse. Physical hardware success is not an accounting write.
- `cashier_shifts`: id/store/drawer/terminal/cashier; state/version/opened_at/closing_at/closed_at; opening_amount>=0; last_cash_sequence; one active or submitting shift per drawer and one per cashier/store via partial unique indexes; actor/terminal/store FKs.
- `cash_movements`: id/store/drawer/shift/operation/source_key/type; cash_delta; balance_before/after; amount>=0; reason/approval/actor; sale/payment/refund/digital/closeout refs; occurred_at_local/created_at; ledger_sequence identity; immutable; unique(operation,source_key,type); CHECK(after=before+delta). A positive opening balance posts one opening movement; a valid zero opening balance records no movement. `closing_count` is an observation with delta0 and amount=counted; all other zero-delta movements reject. Outflow availability accounts for active cash reservations.
- `cash_reservations`: id/store/drawer/shift/service_or_refund/amount/state/operation; outgoing holds, unique source; no cash movement until actual exchange. `cash_reservation_events` is an append-only reservation lifecycle log keyed to POS operations; active holds are included in the locked cash projection.
- `payment_cash_links`: store/payment/movement/operation/allocated_amount; unique(payment,movement); amount magnitude bounded by original payment and movement under source lock. A service's fee payment can link a slice of a larger preposted cash collection; principal remainder links service clearing. Physical sale/refund links full net cash amount. `payment_service_links` similarly links payment to external settlement/clearing fee slice, with source uniqueness. Link rows are append-only, so pending-service cash facts need not be edited at completion.
- Cashier shift balance projection is opening+nonopening delta. Cash movement before/after belongs to that shift, not a global running drawer total that counts every opening again. Late old-shift facts update old expected reconciliation, not current available cash already included in its counted opening. A shortage is a flagged reconciliation issue, not permission to post unauthorized negative cash. Legacy periods remain legacy closeouts without fabricated shifts.

`customers`: id/store/display_name/phone optional/email optional/active/created_by/created_at/updated_at/version/archive metadata; no auto-unique name/phone; contact fields are readable only through the manage-customers RPC and are omitted from cashier search results. ### M12 — Offline leases, stock escrow and ingestion (T49–T55)

`offline_authorization_leases`: id/store/terminal/shift/cashier/issue_operation/prepared_at/issued_at/expires_at/last_mfa_at/activated_at/state/catalog_version/price_policy_hash/sequence_start/end/contract_version/version. `pending_stock` records capture identity/time/sequence but cannot authorize checkout; T52 atomically attaches quote snapshots and activation time before transitioning to `active`. Identity and sequence bounds are immutable; lifecycle changes are versioned and append events. No offline role elevation. Lease defaults are 8 hours and at most 100 terminal operations. `offline_authorization_lease_events` records issue/activation/revoke/expiry/reconciliation append-only. `terminal_sync_cursors`: store/terminal/last_confirmed_sequence/last_reserved_sequence/version; issue locks the cursor and reserves 100 values starting at `last_confirmed_sequence + 1`. Revoking or expiring a still-pending-stock lease returns its known-unused range; an activated lease blocks reissue until reconciliation, and its uncertain range is never reused. `offline_stock_grants`: id/store/lease/product/location/lot/quantity_allocated/quantity_consumed/quantity_released/state/version; 0<=consumed+released<=allocated; unique lease/lot; hold outstanding=allocated−consumed−released. `offline_grant_events`: immutable reserve/consume/release/reconcile with operation, positive quantities and unique source. `offline_sync_conflicts`: operation/store/lease/code/details/state/reviewer/decision/events; preserve payload hash/evidence even if lease revoked.

Price snapshots on grants include original option conversion, permitted net unit price and discount ceiling. Ingest validates grant ownership, quantity and quote rather than current price; archived/recalled product handling conflicts for review, never silently reprices cash already collected. Reserve exact lots, so existing consignment cost/ownership remains deterministic. Same operation ID and original source line creates one movement; duplicate batch returns previous ack. No successful “offline_sync_adjustment” on every retry: ordinary synced sale is sale_deduction with offline metadata; adjustment category is only an explicit reconciliation correction.

## Migration sequence and compatibility

1. T00 isolated baseline → T01 safe test harness → operations/capabilities M01.
2. Shadow M02 structure/backfill → centralized stock writer/cutover. No offline/financial new path enabled yet.
3. M03 accounting normalization and narrow reporting correction; compare old/new fixtures, preserve unknowns.
4. M04–M06 approval/return/refund entities/services. Core financial actions stay gated until M07 drawer integration; temporary deployments may expose read-only/request-only screens.
5. M07 physical cash/shift integration, then M08 closeout snapshot/review/amendment. Switch all supported cash sale/refund/void paths to new movements atomically before enabling them.
6. M09–M10 manual digital catalog/wallets/steps/reconciliation after accounting/cash foundation.
7. M11 customer reads/rankings; shopping-list printing has no DB migrations and can progress independently after foundation contracts.
8. M12 and client IDB/app-shell/security tasks; offline escrow enabled only after full stock/cash/closeout and recovery acceptance.
9. Contract old entry points and generic mutation replay only after old clients receive upgrade-required and pending work is inventoried. Never silently drop legacy queue or data.

Per release: backup → restore rehearsal → additive migrate isolated → migration/authorization/concurrency checks → staging snapshot/validation → short writer cutover if needed → deploy flags off → pilot → reconcile → enable eligible stores. Record applied checksum and effective function fingerprints. Dynamic function text replacements are not the pattern for new migrations; ship full reviewed function definitions.

## Backfill and rollback

Backfill batches use stable PK ranges and checkpoint tables/manifest; compare row counts, sums, lot ownership and sampled receipt hashes before/after. Do not use product names or note parsing to infer customer identity or undocumented external settlement. Legacy void/return note parsing may be used only to label high-confidence provenance in a reviewed report; ambiguous records remain legacy.

Schema rollback before writes: disable flags, restore former functions from captured definitions, leave additive nullable columns/tables. After ledger writes: stop new affected writes, preserve facts and reservations, reconcile projections, ship compensating forward migration. Never delete movements/credits to recover old totals. Rolling back frontend alone is unsafe if it bypasses required shift/operation fields; gateway must reject incompatible old clients. Destructive restore is an incident procedure into a replacement project from verified backup, never routine down migration on live financial history.

Offline client downgrade cannot discard a v2 IDB store. Keep encrypted recovery/acks and prevent older code replay; expose export/recovery guidance. Native printer rollback is independent because shopping-list endpoint is additive and never alters receipt schema.
